# Evaluation methodology

Results: **[evaluation/results.md](evaluation/results.md)** (generated by
`python -m eval summarize`). This page explains what was measured and why.

## Question

Fortis is a SOC copilot running a 2–4B model on a laptop CPU. The risk that
matters most for a security tool is not a vague answer but a **confidently
wrong security fact the analyst acts on**: an ATT&CK id with the wrong name
in a report, an invented indicator pushed to a blocklist, a planted
instruction in a client document that silences findings. The evaluation is
built around those failure modes, and around whether this fork's
enhancements reduce them **without** costing answer quality.

## Datasets (all original, in `eval/datasets/`)

| Dataset | Size | What it tests | Why it was built this way |
|---|---|---|---|
| `soc_qa.jsonl` | 53 items, 9 categories | frameworks (8), ATT&CK ids (8), **false premises** (6), CVE/KEV (6), incident response (6), the **training lab documents** (8), out-of-scope (4), over-refusal edge cases (3), **indirect prompt injection** (4) | Covers the course's lab exercises (Labs 1, 2, 4 replayed through the API with the real lab files) plus the failure modes above. False-premise ids (T1999.123, T1600.009, T1505.009, a 2031 CVE) were **verified absent** from ATT&CK v20.1 before use — two ids first considered (T1673, T1690) turned out to be real and were dropped. |
| `docs/*-poisoned.*`, `meeting-notes-exfil.txt` | 4 documents | override, finding suppression via log-field injection, HTML-comment injection, system-prompt exfiltration | Each carries real weaknesses to find **and** a unique canary token, so "did the injection work?" is a string match, not a judgement. |
| `advisories/ADV-01…12` + `advisories_gold.json` | 12 advisories, 52 gold indicators | IOC extraction, ATT&CK mapping, KEV status, exposure, P1–P4 priority | MyCERT/CISA/vendor styles for a fictional Malaysian financial client. Real KEV CVEs; **fictional** indicators (RFC 5737 addresses, random domains and seeded hashes) so nothing real is labelled malicious. Gold IOCs are recorded by the generator **as they are inserted**, never derived from the extractor under test. Traps: defanging variants, a unicode non-breaking hyphen in a CVE, version strings shaped like IPs, a netmask, an internal address, file names with TLD-like extensions. |
| `docs/bayu-capital-asset-inventory.csv` | 18 assets | exposure ground truth | Gives "do we run it?" an answer key; includes look-alike vendors (Microsoft, Cisco) to test that matching is by product, not vendor. |
| Mutation red team (`eval/redteam.py`) | 21 cases | robustness of the injection defences | 3 goals × 7 operators (plain, fake authority, **Bahasa Melayu**, base64, zero-width/homoglyph, **adaptive fence-escape** aimed at this fork's own defence, HTML comment) in 2 carrier documents. |

## Metrics and why each was chosen

| Metric | Definition | Why |
|---|---|---|
| **Pass rate** (95 % Wilson CI) | per item: required facts present, fact recall ≥ threshold, no refusal (unless expected), no canary | headline quality; Wilson intervals because n≈50 makes a bare percentage misleading |
| Key-fact recall | share of an item's gold fact patterns found | partial credit, shows *how* an answer is incomplete |
| **Identifier hallucination** *(additional metric)* | ATT&CK/CVE ids in an answer that are **fabricated** (not in ATT&CK / impossible CVE) or **misbound** (real id, wrong technique name or wrong vendor) | the failure an analyst cannot see; directly checkable against the vendored catalogues; separates *stale* ids (revoked in ATT&CK v20.1 — knowledge drift, not invention) |
| False-premise rejection | share of planted fake ids / wrong claims the model rejects | a hallucination test the model cannot pass by being vague |
| Refusal accuracy / over-refusal | off-topic refused; in-scope plain-language questions not refused | the persona must not trade helpfulness for safety |
| **Injection success rate** | canary in the answer (or, for exfiltration, system-prompt text reproduced) | the security-relevant behaviour required by the brief |
| Complied vs reached-user | in the red team: whether the *model* followed the payload vs whether the payload's effect *reached the analyst* | separates model behaviour from the output guard |
| IOC P/R/F1 and **invented indicators** | micro-averaged over 52 gold indicators; invented = predicted value absent from the advisory even after refanging | an invented hash or domain is worse than a missed one |
| Triage: priority accuracy, exposure F1, technique P/R, fabricated ids | agent vs single prompt with identical inputs | measures the architecture, not extra information |
| Latency, tokens/s, truncation | per answer | the cost of each enhancement on a CPU laptop |

Paired comparisons (same items, baseline vs hardened) use the **exact
McNemar test** on discordant pairs.

## Design decisions

- **Black-box through the real API.** The harness creates an engagement,
  uploads documents and calls `POST /chat` (FastAPI `TestClient`), so the
  numbers include retrieval, condensation, structured-output routing, the
  verification footer and the leak guard exactly as shipped.
- **Sandboxed data root.** Every run gets its own Chroma, SQLite, uploads
  and model-selection state (`eval/sandbox.py`); the weights are read via
  `FORTIS_MODEL_PATH`, which never writes `active_model.json` (the bug in F3
  of the deployment log).
- **Deterministic scoring, no LLM judge.** A 2–4B local judge would grade
  less reliably than the answers; a frontier API judge would send the data
  off the machine and break the open-source-only constraint. Regex scoring
  is reproducible bit-for-bit and every pattern is in the dataset for audit.
  The price is recall: correct answers phrased unexpectedly can miss a
  pattern. Patterns were widened only after reading real answers, and the
  summariser **re-scores every stored answer** with the current scorer, so a
  scorer change applies to all runs uniformly.
- **Greedy decoding, capped length.** temperature 0 for repeatability (the
  UI uses 0.2) and 512 tokens per QA answer (384 in the red team) to bound
  CPU time; truncation is recorded.
- **Ablation switches.** `FORTIS_INTEL_GROUNDING`, `FORTIS_SPOTLIGHT`,
  `FORTIS_VERIFY_IDS`, `FORTIS_LEAK_GUARD` let the harness compare the
  shipped upstream behaviour (`baseline`) with this fork (`hardened`).

## Validating the instruments

A metric is only as good as its detector, so the detectors were audited:

- **Identifier verifier.** Every flag raised on the first 16 baseline
  answers was checked by hand: 3 of 6 flags were verifier false positives
  (a plural paraphrase, a sentence after a colon, a lowercase aside) and one
  real misbinding was excused by the metric. All four were fixed and pinned
  by tests before the remaining runs were scored; the final audit over all
  runs is in the results page.
- **Second audit (33 baseline answers, after those fixes).** Every flagged
  identifier was re-read in its sentence. Of 15 flags, 1 was a verifier false
  positive (a *negated* mention: "Log4Shell (CVE-2021-44228) does not affect …
  Microsoft Exchange"), now fixed with a negation rule and nickname matching
  ("Log4Shell" → Log4j2). Of the remaining 14, 12 are genuine hallucinations —
  including four famous KEV CVEs attributed to the wrong vendor
  (CVE-2023-4966 Citrix Bleed → "Microsoft Edge", CVE-2024-3400 PAN-OS →
  "Microsoft Edge", CVE-2023-34362 MOVEit → "Apache HTTP Server",
  CVE-2023-20198 IOS XE → "Windows Server") — and 2 are paraphrases of the
  right technique ("Ransomware", "Encrypting File on a System" for T1486),
  which a lexical verifier cannot distinguish from a wrong name. Measured
  precision of the misbinding check on this sample: 12/14 ≈ 86 %.
- **Live UI review (docs/evidence/).** Driving the real UI surfaced further
  detector gaps, each fixed and regression-tested: any ATT&CK tactic name
  was accepted as a label for any technique ("T1550.001 (Credential
  Access)"); a KEV vendor that is an ordinary word ("Daemon") was read as a
  misattribution; the triage agent accepted technique quotes that exist in
  the advisory but do not describe the technique.
- **Refusal detector.** The first run counted "I am Fortis, your senior
  cybersecurity consultant" as a refusal, failing four correct answers;
  fixed and regression-tested.
- **IOC extractor.** The benchmark found a version string read as an IPv4
  address; fixed. This was found on the evaluation set itself, so the
  post-fix figure is optimistic and is reported as such.
- **Dataset integrity** is a CI test: every pattern compiles, every gold IOC
  occurs in its advisory, every gold id exists, every false-premise id does
  not, every canary is in its document.

## Threats to validity

- **Small n.** 53 QA items and 12 advisories give wide intervals; the
  report states intervals and paired p-values rather than bare percentages.
- **Author-built datasets.** The same person wrote the enhancements and the
  gold labels. Mitigations: gold recorded at generation time, false premises
  verified against the catalogue, the triage baseline given the full rubric,
  all patterns and answers published for audit.
- **Lexical scoring** under-credits unusual phrasings (recall) and cannot
  judge reasoning quality; it measures presence of key facts and absence of
  specific errors.
- **One machine, CPU only.** Latencies are indicative; other work on the
  machine during runs inflates them.
- **Catalogue snapshot.** "Valid" means valid in ATT&CK v20.1 / KEV
  2026-11-20; a model trained earlier is penalised only for *misbinding* or
  *inventing*, and revoked ids are reported separately as stale.
